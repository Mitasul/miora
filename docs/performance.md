# 性能优化与复测

本轮针对请求热路径和确定冗余代码，不改变渠道协议、认证、插件热更新语义或日志隐私默认值。不增加依赖，不以扩大内存预算、降低脱敏强度或减少留存内容冒充性能优化。

2026-10-16 的后续调用链检查与删减记录见 [重复检查清理](defensive-code-audit.md)，包括流式/错误正文摘要、插件重复校验、无规则请求头解析和后台同源响应兜底。本轮没有新的端到端性能对照，不把历史测量套用于这些变更。

## 测量方法

- 基线与候选均使用相同的 Windows GNU `release` 构建，`--locked --offline`；不把 debug 切换到 release 的收益混入代码对比。
- 使用独立临时配置、SQLite、日志目录、测试凭据和回环模拟上游，不访问生产或付费供应商。当前 8000 预览不参与压测。
- `tests/perf/benchmark_gateway.py` 覆盖 0 / 256 个启用插件、日志关闭、仅摘要、SSE 摘要和 SSE 正文捕获。
- 每场景三轮；报告吞吐和请求延迟的中位值，以及日志队列排空时间、写入错误、内容丢弃计数和记录中的采集失败原因。
- HTTP 测量包含 Python 模拟上游、客户端及本机文件系统，不是纯 Rust 性能，也不代表 WAN 或生产容量。
- 压力组若触发日志预算保护，不能仅看更高吞吐宣称优化有效。另有单并发、响应后固定 20ms 间隔的正文捕获延迟对照；其吞吐包含人为间隔，不能作为容量指标。
- 定向内部检查用于确认快照复用、缓冲增长、锁/构造次数等收益机制，不能直接换算成整个网关或页面的加速倍数。

示例（比较时二进制必须是相同构建档位）：

```powershell
cargo build --release --locked --offline --target x86_64-pc-windows-gnu
python tests/perf/benchmark_gateway.py .artifacts/performance/baseline-gateway.exe --output .artifacts/performance/baseline.json --rounds 3 --requests 160 --concurrency 4 --plugins 256
python tests/perf/benchmark_gateway.py .artifacts/performance/candidate-gateway.exe --output .artifacts/performance/candidate.json --rounds 3 --requests 160 --concurrency 4 --plugins 256
python tests/perf/benchmark_gateway.py .artifacts/performance/candidate-gateway.exe --output .artifacts/performance/candidate-capture-paced.json --rounds 3 --requests 120 --concurrency 1 --plugins 256 --only-logging capture --pacing-ms 20
```

优化前二进制在任何生产源码修改前保存，避免用修改后的代码重新构造“基线”。新增测试脚本只读取内部格式来创建独立 fixture，不修改实际插件存储。

## 精简与安全边界

- 删除无引用的 `SettingsSnapshot::captures` 和多余类型转导出；仅测试使用的类型改在测试中直接导入。保留实际配置类型及序列化接口。
- 复用固定语言的 `Intl.NumberFormat`；保留数字类型、有限数检查及未知值的原有输出。
- 删除会话失败页的重复刷新监听，保留统一事件委托、错误提示、登录入口及键盘按钮行为。
- 删除确认未用的前端导入和只写变量，不删除仍在内部使用的导出实现。
- 日志 Begin 的摘要及八个 pending 字段在一个纯 SQL 事务内写入；初始化失败不能遗留半条记录。复用热点 prepared statement，不把带文件写入/淘汰副作用的 finish 强行包进事务。
- 插件快照优化必须保留发布失败不生效、旧请求固定旧版本、启停/更新/回滚与拦截器变更一致发布，以及 EOF/取消后释放引用。每次成功发布无条件保存上一代快照的 Weak，并在后续发布时清理已经失活的 Weak；不能用发布瞬间的强引用计数决定是否登记旧代。管理界面的 `lease_count_kind="snapshot_references"` 不是精确请求数。
- 日志缓冲优化必须同时核算实际容量和已保存字节；保留全局及单请求上限、未选择头但正文需要脱敏时的凭据收集、观察字节数和终态信息。缓冲在配额内倍增，配额压力时才回收其他字段的空余容量，失败清理同步归零容量账本。
- 文本脱敏为每个凭据缓存下一次匹配位置；已经确定不存在的模式不再对每个后缀重搜，仍按最早位置、同位置最长匹配进行一次性替换，不重新扫描替换标记。
- 头字段序列化借用同一锁内的敏感信息和头集合，避免整份凭据深拷贝与逐项临时 JSON 对象；最终序列化结果收紧容量后再交给保存内容预算记账。

## 本轮验证结论

**结果：功能回归通过，局部热路径机制有效；尚未证明稳定的端到端性能提升，因此未替换或重启 8000 预览。** 不把未达门槛的候选称为已验收部署。

- Windows GNU release、锁定离线：库回归 360 通过、0 失败；随后单独执行原先 ignored 的两项 release 微基准，均通过。
- HTTP fixture 32 个脚本及真实 supervisor 1 个脚本全部通过，共 33/33；包括真实插件热更新/旧流 draining、日志与隐私、参数策略、原始流与重试/超时。
- 前端 Node 50/50、运行日志轮转 7/7、真实 Chrome 12 组通过。Chrome 覆盖九个路由、CRUD、密钥不回显、移动端、logout，并在独立的已认证浏览器上下文中注入 session HTTP 503，验证指针/键盘各只刷新一次。此故障注入不冒充真实后端成功。
- 最终复核由当前助手直接完成；用户要求停止所有 Agent 后没有再派发或续派，不声称获得独立 Agent 的最终签字。

### 已验证的局部机制（不换算成整体加速倍数）

- 同一 release 测试二进制，32 次 × 1 MiB、512 字节分块：容量增长次数从 65,536 次降为 352 次；两侧单缓冲峰值均为 1 MiB，未扩大限额。
- 8 KiB 分块的同项检查：4,096 次降为 256 次；峰值同样不变。
- 测试头集合每次处理的锁入口从 17 次降为 1 次；开启原始头捕获时两侧每次保存 443 字节，输出一致。
- 当前快照 pin 在 0 / 1 / 128 插件时分别约 61.6 / 66.5 / 62.0 ns/次；验证复用和插件数不再驱动每次重建，不据此推算 HTTP 提升。
- 250 个相同有限数输入的格式化输出一致，formatter 构造 250 次降为 1 次；这不是页面耗时倍数。

### 端到端压力对照

下表范围为最近两次独立运行各自“三轮中位数”的范围，不是置信区间。每轮 160 请求、并发 4，fixture / 上游 / 客户端 / 构建档位相同；使用原先保存的优化前二进制，未重新生成基线。

| 场景 | 基线请求/秒范围 | 候选请求/秒范围 | 解释 |
| --- | ---: | ---: | --- |
| 0 插件，日志关闭，非流 | 507.71–509.62 | 493.05–508.77 | 未证明稳定改善 |
| 256 插件，日志关闭，非流 | 475.48–518.20 | 452.21–497.11 | 波动明显，不能宣称更快 |
| 256 插件，仅摘要，非流 | 429.69–492.27 | 486.14–488.82 | 基线波动覆盖候选，不能只选低基线报收益 |
| 256 插件，仅摘要，SSE | 286.70–295.77 | 295.61–297.67 | 幅度小，未证明稳定整体收益 |
| 256 插件，正文捕获，SSE | 291.81–293.27 | 177.92–268.71 | 捕获工作量不等，不作容量或加速比较 |

正文压力组必须与失败指标一起阅读：

- 最近两次基线累计捕获失败分别 187 / 271 条，均为 `capture_metadata_budget_unavailable`；对应测量轮次 `dropped_content_records` 增量均为 0、writer failures 均为 0。只读一个丢弃计数会漏掉预算保护导致的捕获失败。
- 候选第一次累计失败 209 条（预算不足 203、`queue_full` 6）；测量轮次丢弃计数累计增量 42、writer failures 0。计数器增量不是“唯一失败行数”。
- 候选第二次累计捕获失败、丢弃增量及 writer failures 全部为 0，但吞吐 177.92 请求/秒、p95 44.12 ms；相较有失败的基线实际做了更多日志工作，不能据此简单判为加速或减速。
- 原始历史基线的 66 / 133 条失败及相应 JSON 仍保留；没有删去不利数据。

### 零失败、完整正文的配对延迟

单并发、每次响应后固定等待 20 ms；每侧每次三轮 × 120 请求，另有 12 次暖身。耗时不含人为等待，吞吐包含等待，因此不作为容量指标。后两组按 ABBA 顺序执行；均无其他构建或测试负载并发。

| 配对组 | 基线 p50 / p95，ms | 候选 p50 / p95，ms |
| --- | ---: | ---: |
| 首组 | 6.114 / 8.372 | 5.839 / 7.718 |
| 第二组 | 6.963 / 8.449 | 7.076 / 8.489 |
| 第三组 | 7.156 / 8.585 | 7.207 / 8.642 |

首组优势未在后两组复现，故不声称稳定的端到端延迟改善。每组双方捕获失败、丢弃计数增量及 writer failures 均为 0。第二、第三组额外查询 SQLite，双方每次均为 372 条记录、744 个 available 且 complete 的正文；每个正文阶段累计保存 15,289,944 字节、观察 15,908,952 字节，两侧完全一致。保存字节少于观察字节来自同样的解析/脱敏序列化，不是以截断冒充完整。

### 已处理的测试环境/fixture 问题

- 初次 HTTP 矩阵在旧 fixture 以 Windows 默认 GBK 读取 UTF-8 目录 JSON 时退出；运行环境明确 `PYTHONUTF8=1` 后完整重跑通过，没有改协议或删测试。
- 浏览器旧渠道模型定位器已过时，改为实际“模型”页的手动添加控件，仍验证真实 CRUD 与未改动 URL 中密钥保留。
- 故障注入页必须先真实登录，才能通过服务端文档鉴权进入 app；未登录的 `/admin` 正确跳转 `/login`，不是产品错误。修正此前置条件后完整重跑通过。两次失败报告保留在 browser/attempt-*。

构建、前后测量、直接复核与回归产物位于 `.artifacts/performance/`：重点查看 `acceptance.json`、`http-report.json`、`browser/browser-report.json`、`review.md`、`microbench-results.json`、`baseline-{current,final}.json`、`candidate{,-repeat}.json` 和 `*-paced-pair{2,3}.json`。最终候选是 `candidate-gateway.exe`；`candidate-build-final.log` 对应无条件 Weak 修复后的实际构建，不与较早的 `candidate-build.log` 混用。

## 2026-10-15：价格快照与主题切换

- 用量写入之前重复递归校验所有模型价格，并把完整价格目录复制、序列化到每条请求。现在只查找当前公开模型，提取至多五个适用单价；全表结构校验仍保留在渠道保存边界，所选单价的数值范围校验和输入 / 缓存一致性检查继续保留。显式免费、模型覆盖、null 未配置与历史价格快照语义不变。
- 定向用例中，500 模型的价格目录为 25,957 字节，当前模型快照为 58 字节。此数字仅衡量该测试的价格 JSON，不是整个请求日志体积、延迟或网关吞吐改善比例。真实 SQLite / JSON / SSE 回归另外检查无关的 500 项价格不进入请求快照。
- `/usage` 已由专用投影直接构造固定字段、公开模型名和固定密钥掩码，不再重复写入 `available`、遍历改写相同掩码，或对该 DTO 执行通用配置脱敏的递归复制。原始配置、渠道和插件响应的脱敏逻辑不变；该统计查询不读取或返回原始密钥。
- 设置保存不再先 POST 校验再 PATCH；PATCH 本身保留服务端校验和修订冲突处理，「仅校验」仍单独可用。有限数字直接比较，不为比较两个数进行 JSON 序列化。渠道保存复用已经验证的模型列表，参数策略只解析一次，校验失败仍切到对应页签。
- 不删除认证、CSRF、修订冲突、日志脱敏、流控、未知用量与真实零值区分等必要检查。不为省分支改变失败处理或资源预算。
- 主题只更新根节点的 CSS 变量，不重新请求统计或重建页面。共享一份同源小型脚本；启动读取一次偏好，仅在系统配色 / 手动选择 / 跨标签页事件时更新，无轮询和新依赖。禁止存储的异常只在浏览器存储边界处理。
- 功能验证包含 Rust 库测试、前端模块与静态契约、真实 Chrome 浅色 / 深色全路由、窄屏表单 / 日志抽屉、系统切换、刷新保留、跨标签页同步、禁用存储及真实用量 HTTP 回归。产物位于 `.artifacts/theme/`。本轮未做新的端到端吞吐对照，不宣称整体加速倍数。
